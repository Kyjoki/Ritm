## Что меняется в хранилище

Локальный режим использует SQLite. При настроенном `DATABASE_URL` сервер
использует `PostgresStore` из `server/postgres-store.ts`. Его конструктор не
выполняет SQL, миграции, удаление записей или заполнение примерами.

Методы сохраняют JSON-контракты задач, настроек, диалогов и предложений ИИ.
API ожидает результаты через `await`; SQLite может возвращать их синхронно.
Общий контракт находится в `server/repository.ts`.

PostgreSQL содержит таблицы с префиксом `ritm_`:

| Таблица                                    | Назначение                                                             |
| ------------------------------------------ | ---------------------------------------------------------------------- |
| `ritm_tasks`, `ritm_deleted_tasks`         | Задачи и последние 50 удалений для восстановления                      |
| `ritm_finance_entries`                     | Ручные финансовые записи; создаётся явной миграцией `002-finance.sql`  |
| `ritm_conversations`, `ritm_chat_requests` | История и идентификаторы обработки сообщений                           |
| `ritm_config`, `ritm_workspace`            | Настройки и блокировка единого пространства                            |
| `ritm_sessions`, `ritm_rate_limits`        | Общие для экземпляров сессии и ограничения запросов                    |
| `ritm_server_secrets`, `ritm_leases`       | Зашифрованные подключения, OAuth state и временное владение операциями |
| `ritm_schema_migrations`                   | Применённые миграции                                                   |

Все изменения используют интерактивную транзакцию `pg.Pool`, advisory lock
одного пространства и `SELECT ... FOR UPDATE`. Проверка версий и пересечений
расписания происходит до записи в той же транзакции. Чтение `bootstrap`
получает согласованный снимок. Запрос к модели выполняется за пределами
транзакции и не удерживает соединение базы во время ожидания OpenAI.

На Neon pooling не сохраняет startup-параметры server timeouts. Поэтому
каждая транзакция выполняет `SET LOCAL statement_timeout = '15s'` и
`SET LOCAL lock_timeout = '5s'` до получения блокировок. Клиентский timeout —
16 секунд. Реальная проверка двух соединений подтвердила единственного winner
lease, общие CRUD-данные, полный rollback частичной записи предложений и
эффективные значения таймаутов. Временные записи проверки удалены строго по ID.

## Повторы и перезапуски

Первый запрос чата получает случайный `leaseToken` на 180 секунд; вызов
модели ограничен 90 секундами. Другой экземпляр видит активную обработку.
В одном диалоге нельзя одновременно резервировать второе сообщение.
Завершённый requestId возвращает существующий диалог; изменение текста
при повторном использовании того же requestId отклоняется.

После истечения lease следующий обработчик может занять тот же запрос.
Старый обработчик не может сохранить ответ или освободить новый lease.
Cold start не удаляет чужие running-записи. Неизвестный исход прерванного
внешнего запроса не даёт гарантии отсутствия повторной оплаты OpenAI;
сохранённые завершённые запросы повторную генерацию не выполняют.

Сессии и ограничения хранятся в PostgreSQL. OAuth state извлекается
одноразовым `DELETE ... RETURNING`. Обновление токенов Google использует
именованный lease, который может освобождать только получивший его
обработчик. Файлы `data/.secret-key` и `openai-secret.json` для облачного
режима не подходят: постоянный ключ шифрования задаётся серверным секретом,
а шифротекст сохраняется в базе.

## Раздача интерфейса

Vite собирает приложение в `build/client`. В Vercel этот каталог должен
публиковаться как статический CDN output, а `/api/*` направляться в API
handler. Конфигурация должна проверяться целиком: ответ HTML, JS/CSS,
favicon, защищённый API и login cookie на одном origin.

В репозитории добавлены `vercel.json` (Vite preset, Node.js 24, API timeout
180 секунд) и ленивый `api/index.ts`. `/api/*` направляется в общий handler,
остальные пути — в SPA. На настоящем Preview нужно проверить, что rewrite
сохраняет исходные пути Express, включая OAuth callback и query parameters.
Успешный локальный API-тест не заменяет эту проверку платформенной маршрутизации.

`api/tsconfig.json` изолирует транспиляцию Vercel Function от клиентских
глобальных `vite/client` и dev-only type packages. Полная проверка типов
всего приложения, включая API, остаётся в корневом `npm run build` и CI.

При выборе native Express preset `express.static()` игнорируется:
статические файлы публикуются Vercel отдельно. Простая загрузка текущего
SQLite-сервера с локальной файловой раздачей не создаст работающий облачный
сайт. Используйте Vite output + API handler либо явно подготовленный
Express CDN output. [Express на Vercel](https://vercel.com/docs/frameworks/backend/express),
[Vite на Vercel](https://vercel.com/docs/frameworks/frontend/vite).

## Окружение

Секретные значения не помещаются в Git, `VITE_*`, HTML, логи или сообщения
чата. Production и Preview используют разные базы и серверные секреты.

`.vercelignore` отдельно исключает локальные `data`, SQLite, `.env*`,
`.vercel` и provider skills из deployment upload. Одного `.gitignore`
для Vercel CLI недостаточно. Перед первым выпуском `vercel deploy --dry --json`
подтвердил: 88 файлов, локальных баз/секретов в списке отправки нет.

| Переменная              | Назначение                                                        |
| ----------------------- | ----------------------------------------------------------------- |
| `DATABASE_URL`          | Серверное подключение к выбранному PostgreSQL                     |
| `APP_LOGIN`             | Логин единственного владельца                                     |
| `APP_PASSWORD`          | Длинный уникальный пароль владельца                               |
| `APP_SESSION_SECRET`    | Постоянный случайный секрет сессий, не менее 32 байт              |
| `SECRET_ENCRYPTION_KEY` | 32 случайных байта в base64 либо 64 hex-символа                   |
| `APP_ORIGIN`            | Точный HTTPS origin приложения без пути                           |
| `OPENAI_API_KEY`        | Необязательный серверный OpenAI key; иначе настройка в интерфейсе |
| `OPENAI_MODEL`          | Название модели, по умолчанию `gpt-6-luna`                        |

Для Google нужны отдельные серверные OAuth credentials; имена и настройки
callback описаны в `docs/google-calendar.md`. Ключ шифрования нужно
резервировать отдельно от базы. Его смена без перешифрования сохранённых
подключений потребует их повторной настройки.

Standalone scripts и Express не получают `.env.local` автоматически.
Команда миграций должна явно загрузить локальное окружение. Production и
Preview Secret values могут отсутствовать в результате `vercel env pull`:
для локальной разработки используйте отдельные Development credentials.
Проверяйте имена переменных, не печатая значения.
[Переменные окружения Vercel](https://vercel.com/docs/environment-variables).

## Порядок подключения

1. Выберите аккаунт/scope и конкретный проект Vercel. На этапе подготовки
   доступный коннектор вернул пустые списки проектов, команд и интеграций;
   наличие ресурсов в другом аккаунте этим не проверено.
2. Привяжите репозиторий к выбранному проекту. До проверки привязки не
   запускайте миграции и не перезаписывайте существующее окружение.
3. Проверьте существующий Neon. Доступный ресурс можно подключить через
   `vercel integration resource connect <resource-name> <project> -e production`.
   Указывать окружение нужно явно: по умолчанию подключаются все три.
   Не запускайте `integration add` повторно для поиска существующей базы —
   эта команда может создать новый ресурс.
   [Подключение Marketplace resource](https://vercel.com/docs/cli/integration).
4. Настройте серверные переменные и отдельную Preview базу/ветку. Проверка
   конфигурации должна подтвердить конкретную целевую базу, а не только
   наличие строки `DATABASE_URL`.
5. Примените миграции отдельной командой:

   ```powershell
   npm run db:migrate
   ```

   Runner `migrations/migrate.ts` применяет SQL и запись версии в одной
   транзакции. Повторный запуск не перезаписывает существующие настройки.
   Он не импортирует локальную SQLite автоматически. Существующие личные
   данные следует сохранить и перенести отдельным проверенным импортом.

6. Запустите локальную проверку с настоящим PostgreSQL. Убедитесь, что новый
   экземпляр сервера видит задачи, сессии, отмену действий и историю первого.
7. Создайте Preview и проверьте интерфейс/API на его точном origin. Для
   настоящего Google OAuth нужен зарегистрированный стабильный callback;
   случайные preview URL нельзя автоматически считать разрешёнными Google.
8. После проверки Preview и настройки production origin выполняйте выпуск.

Production-выпуск разрешён пользователем после усиления защиты.

Ресурсы и production migrations выполнены. OpenAI и Google OAuth credentials
пока не заданы. Полная проверка их реальных ответов требует этих настроек.

Для staged production сервер дополнительно принимает только точный HTTPS
адрес текущего deployment из серверного `VERCEL_URL` при `VERCEL=1`.
Другие `*.vercel.app`, request forwarded headers и произвольные origin
не разрешаются. Постоянный origin остаётся `APP_ORIGIN`.

## Защита на границе Vercel

Серверные ограничения и шифрование включены в код. Правила WAF для проекта
ещё не созданы. [Автоматическая DDoS-защита](https://vercel.com/docs/vercel-firewall)
Vercel действует после размещения на платформе; её работу здесь не проверяли.

Для первого Hobby-проекта подготовлено одно правило ограничения API:
фиксированное окно 60 секунд, 1000 запросов на IP, все `/api`-пути. Значение
взято с запасом для обычной ручной работы и проверяется на настоящем трафике.
На [Hobby доступно одно правило rate limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting);
счётчики Vercel региональные. Это дополнительный предел до обращения к API,
а не замена общим ограничениям приложения.

После привязки нужного проекта команда создаёт только черновик в режиме Log:

```sh
vercel firewall overview
vercel firewall rules add "Ritm API traffic" --condition '{"type":"path","op":"re","value":"^/api(?:/|$)"}' --action rate_limit --rate-limit-window 60 --rate-limit-requests 1000 --rate-limit-keys ip --rate-limit-action log --yes
vercel firewall rules inspect "Ritm API traffic"
vercel firewall diff
```

Эти команды здесь не выполнялись. Владелец публикует черновик после просмотра
diff, проверяет совпадения в Firewall → Traffic и сохраняет обычный трафик.
Затем правило проверяется с блокировкой на Preview и только после этого
переводится в production. Для блокировки используется стандартный ответ 429;
challenge не добавляется к JSON API или OAuth callback. Общий фильтр по
стране, браузеру или user-agent не используется.

В настройках наблюдения ищите `request_blocked`, `server_error`, `login_success`,
`logout`, `google_connected`, `google_disconnected`, `openai_saved`,
`openai_removed`. Приложение не отправляет в эти записи секреты и содержание
задач. Встроенный журнал ограничен по объёму и не заменяет Firewall Traffic.
Настройте закрытый доступ к логам, срок хранения и оповещения после выбора
проекта. Проверяйте отдельно, не сохраняет ли сам хостинг полные callback URL.

## Что проверено и что ещё проверить

`tests/postgres.test.ts` использует **pg-mem**, а не настоящую облачную базу.
Он проверяет SQL-контракты CRUD, повторное открытие репозитория, lease
ownership, дедупликацию, одноразовый state, ограничения и устаревшие планы.
В эмуляторе advisory lock заменён функцией-заглушкой; rollback для
последовательных тестов добавлен snapshot fixture. Это подтверждает
протокол ошибок приложения, но не реальную изоляцию PostgreSQL.

На настоящей Neon дополнительно проверены CRUD через два соединения,
единственный владелец lease, rollback частично записанного предложения и
таймауты транзакций. На Vercel проверены статические ассеты, вход, CRUD,
восстановление и отзыв сессии; отдельные записи проверки удалены.

Для дальнейшей регрессии и настройки внешних подключений остаются:

- Одновременная обработка двух сообщений диалога разными serverless instances.
- Одновременное ручное изменение задачи и применение предложения ИИ.
- Проверка сроков сессии между разными instances.
- Смена owner credentials и постоянных ключей; раздельные Preview данные.
- Настоящий Google consent/callback, обновление и отзыв токенов.
- Настоящий ответ OpenAI после настройки ключа.
- Визуальная и клавиатурная проверка всех экранов на компьютере и телефоне.

Google и OpenAI credentials ещё не настроены. Успешная публикация и
облачные CRUD-проверки не подтверждают работу этих внешних сервисов.
