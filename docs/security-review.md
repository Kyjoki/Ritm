# Проверка безопасности Ritm

Дата: 13 октября 2026 года. Проверена реализация `server/**`, `agent/**`, граница клиентского API и интерфейс подтверждения предложений ИИ. Это обзор текущего персонального приложения; отдельная проверка публичного развёртывания требуется после выбора хостинга.

## Что выполнено

### Усиление защиты по запросу владельца

Проверка ориентируется на [OWASP Top 10:2025](https://top10.owasp.org/2025/)
и [OWASP API4: расход ресурсов](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/).
Это перечни важных рисков, а не статистика частоты атак именно на Ritm.

- Закрытые API проверяют сессию до разбора тела. Вход принимает не более 4 КБ
  JSON, прочие запросы — 128 КБ. Сжатые тела отклоняются до распаковки;
  неподдерживаемые методы, слишком длинные URL и тела GET/HEAD блокируются.
- Ответы API, включая ошибки доступа и парсинга, получают `Cache-Control: no-store`.
  CSP запрещает объекты, встраивание и подмену base URI; добавлены COOP/CORP.
  HTTPS origin получает HSTS без распространения на другие поддомены.
- Генерации ИИ ограничены двумя общими durable leases на личное пространство,
  в том числе между экземплярами сервера и разными диалогами. Ошибка освобождает
  слот; при аварии lease истекает через 180 секунд. Ограничение 10 запросов/минуту,
  90-секундный deadline и 3000 выходных токенов сохраняются.
- Проверка пароля использует асинхронный scrypt с максимум четырьмя
  одновременными вычислениями на экземпляр; вход не блокирует event loop.
  HTTPS-сессия получает cookie `__Host-ritm_session` с `Secure`, `HttpOnly`,
  `SameSite=Strict`, `Path=/`, без Domain. Дублированные auth cookies
  отвергаются. Host проверяется как канонический authority, без credentials,
  пути, query, fragment и числовых псевдонимов loopback.
- Недоверенные тексты задач, профиля, Google-событий и истории вынесены из
  системных инструкций ИИ в отдельное JSON-сообщение данных. Это снижает риск
  подмены инструкций, но не гарантирует поведение модели. Граница изменений
  остаётся серверной: строгая схема ответа, отсутствие инструментов записи,
  выбор и подтверждение владельцем, повторная проверка расписания.
- OpenAI получает только POST на `https://api.openai.com/v1/responses`;
  внешние адреса, query, credentials, другие методы и redirects отклоняются.
  Ответ ограничен 2 МиБ. Точное значение собственного API-ключа скрывается
  в передаваемом контексте; вставка ключа в текущий запрос чата блокируется.
- AES-GCM требует IV ровно 12 байт, тег ровно 16 байт и строгий ограниченный
  envelope с каноническим base64. До исправления Node принимал тег,
  урезанный до 4 байт. Подмена имени секрета также отвергается через AAD.
- Восстановление удалённой задачи повторно проверяет квоту 2000 задач.
  Активные задачи и история ограничены общим бюджетом 8 МиБ JSON в UTF-8;
  отказ происходит до записи или откатывает общую транзакцию. Старые данные
  не удаляются автоматически, удаление остаётся доступным для освобождения места.
  PostgreSQL ограничивает statement 15 секундами, ожидание lock — 5 секундами,
  клиентский запрос — 16 секундами; внешний внедрённый pool сохраняет свои настройки.
- Публичные проверки сессии и OAuth callback получили отдельные клиентские
  ограничения 120/минуту и 20/минуту. Они не расходуют квоту входа и другого
  клиента. `/health` остаётся независимым от доступности базы.
- GitHub Actions закреплены по проверенным commit SHA; CI выполняет
  `npm audit --audit-level=high`. На момент проверки npm audit не обнаружил
  известных уязвимостей. Проверка реестра не гарантирует отсутствие неизвестных
  дефектов или вредоносного кода в зависимостях.
- Добавлены структурированные события входа, выхода, изменения подключений,
  блокировки запросов и ошибок сервера. Журнал содержит только время, тип,
  HTTP-статус и случайный серверный requestId. Пароли, IP, cookies, URL,
  Google-коды, ключи и тексты пользователя не записываются. Объём ограничен
  60 событиями/минуту на экземпляр; отказ журнала не отменяет защиту.

Журнал выводится в stderr сервера, но хранение, оповещения и анализ событий
хостинга ещё не настроены. При большой атаке лимит журнала пропускает часть
событий: для полного учёта нужна отдельная защита и наблюдение на границе.

Проверены уже существующие барьеры: SQL-значения передаются параметрами;
схемы отклоняют дополнительные поля и неподходящие ID; React показывает текст
без `innerHTML`; OpenAI не получает инструментов записи; Google использует
PKCE, одноразовый state и ETag. XSS-пейлоады не удаляются из названий задач:
их безопасность обеспечивается текстовым выводом, а не списком запрещённых слов.

### Предыдущие этапы

Дополнение этапа Google Calendar/Vercel: реализованы постоянные JWT-сессии с отзывом, общий PostgreSQL, одноразовый OAuth state с PKCE и привязкой к сессии. Проверены повторное сохранение Google-события, ETag, ограничения повторений/гостей/DST, выход во время обмена OAuth и лимит контекста ИИ. Вход ограничивается по клиенту; доверие к валидному `x-vercel-forwarded-for` включается только в окружении Vercel. Сырой IP в базе не сохраняется. Итоговый набор проверок — в `docs/verification.md`.

- На первом этапе тесты Node.js 24.19.0: **16 из 16 проходят** — `tests/server.test.ts` и `tests/calendar.test.ts`. Второй независимый обзор добавил 5 проверок в `tests/security.test.ts`; итог всего набора указан в `docs/verification.md`.
- Дополнительно выполнены **10 независимых HTTP-проверок** настоящих маршрутов Express с временной SQLite-базой и тестовым `AssistantRunner`.
- `npm run typecheck` проходит.
- Настоящие ключи не использовались, запросов к OpenAI не было. Внешние ответы в тестах заменены явно заданным mock; это не подтверждает доступность модели или действительность пользовательского API-ключа.

Независимые HTTP-проверки: закрытый `/bootstrap` без сессии; вход и атрибуты cookie; отсутствие ключа в bootstrap; запрет чужого Origin; запрет мутации с `text/plain`; запрет чужого Host; повтор запроса с одинаковым UUID без повторного вызова модели; конфликт при подмене сообщения для того же UUID; отказ на неизвестный taskId без сохранения диалога; удаление диалога без тела запроса.

Готовые серверные тесты дополнительно проверяют шифрование сохранённого ключа, отсутствие ключа в SQLite, logout, отключение ИИ, обязательность пароля при публичном/production запуске, запрет публичного HTTP origin, режим ключа из environment, CRUD и восстановление задач, сохранность данных после открытия новой Store, повторение задач, отклонение некорректного ответа ИИ, атомарное применение выбранных изменений, stale/collision rollback и безопасную отмену после ручного редактирования.

## Проверенные границы

| Граница                      | Реализация и подтверждение                                                                                                                                                                                                                                        |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Доступ к персональным данным | При настроенном пароле защищённые API требуют серверную сессию. Production или bind вне loopback без пароля прекращает запуск. Cookie имеет `HttpOnly`, `SameSite=Strict`, срок 8 часов; `Secure` включается для HTTPS `APP_ORIGIN`.                              |
| Межсайтовые запросы          | API проверяет Host, разрешённый Origin, `Sec-Fetch-Site` и JSON Content-Type для мутаций. Dev-сервер привязан к `127.0.0.1`; доверие произвольным proxy-заголовкам отключено.                                                                                     |
| Ключ OpenAI                  | Передаётся серверу, отсутствует в bootstrap и ответах настройки. Сохранённый ключ находится в AES-GCM-конверте вне SQLite. В репозитории игнорируются `/data/`, `.env`, SQLite и служебные файлы.                                                                 |
| Ответ модели                 | Structured output проходит серверные ограничения формы, даты, времени, длительности и идентификаторов задач. Отсекаются выполненные задачи, встречи, повторяющиеся серии, повторные taskId, прошлое время и предложения без изменения.                            |
| Изменения расписания         | Модель не получает инструментов записи. Пользователь выбирает карточки и отдельно подтверждает применение. API применяет только переданные proposalIds в SQLite-транзакции. Проверяются версия задачи, исходное расписание, текущее время и пересечения.          |
| Отмена                       | Возвращает только выбранные применённые изменения. Ручное редактирование после применения делает старую отмену недопустимой. Ошибка не оставляет частично изменённые задачи.                                                                                      |
| Повтор чата                  | Устойчивый UUID и fingerprint запроса хранятся сервером. Повтор завершённого запроса возвращает существующий диалог без второго вызова модели. Ошибка провайдера не создаёт ложные сообщения и допускает повтор.                                                  |
| Внешний ввод                 | Модель не имеет средств обращения к пользовательским URL или ОС; адрес OpenAI фиксирован. Тексты чата, задач, шагов и причин выводятся React как обычный текст. HTML модели не исполняется. Ошибки провайдера не возвращают его raw payload, заголовки или stack. |

## Найдено и исправлено во время обзора

1. Клиентские мутации без тела не передавали JSON Content-Type. После изменения клиента обнаружено, что Express `req.is()` также не распознаёт Content-Type у запроса без тела. Защита теперь проверяет сам заголовок: DELETE и logout работают при сохранении JSON-барьера.
2. Проверка loopback не учитывала `[::1]` из `URL.hostname`. IPv6-вариант добавлен.
3. `process.loadEnvFile()` при отсутствии `.env` останавливал запуск. Добавлена проверка существования файла.
4. ИИ мог вернуть корректное по форме время в прошлом или предложение без изменения. Добавлены семантические проверки; время повторно проверяется при применении плана.
5. Сохранение ключа не подтверждает реальный доступ к OpenAI. Статус интерфейса изменён на «Ключ настроен»; Google Calendar честно обозначен как неподключённый.
6. Папка данных и файлов шифрования добавлена в `.gitignore` до коммита.

## Ограничения проверки и эксплуатации

- Полная браузерная и визуальная проверка приложения не выполнена: browser security policy отклонила localhost-вкладку; обход ограничений не выполнялся. Публичный экран входа после размещения на Vercel отдельно отрисован во встроенном браузере, остальные экраны и мобильные сценарии не подтверждены. API-тесты запускались с разрешённым доступом к loopback.
- Публичный HTTPS и опубликованный API проверены на Vercel: вход с Secure cookie, 401 без сессии, CRUD/восстановление задач, запрет чужого Origin и отзыв cookie после выхода. Для владельца установлен сгенерированный уникальный пароль. Правила WAF, оповещения и резервное восстановление отдельно не проверены; подробности выпуска — в `docs/verification.md`.
- Приложение рассчитано на одно личное пространство. SQLite требует одного процесса; PostgreSQL хранит общие сессии, лимиты, подключения и данные нескольких экземпляров. На настоящей Neon проверены CRUD двух соединений, единственный winner lease и полный rollback частичной записи предложений. Несколько независимых пользователей не реализованы.
- В локальном режиме ключ шифрования лежит в `data`. Доступ ко всей папке позволяет расшифровать сохранённые секреты; POSIX mode `0600` не является гарантией NTFS ACL на Windows. В PostgreSQL хранится шифротекст, а постоянный ключ задаётся отдельным серверным секретом `SECRET_ENCRYPTION_KEY`.
- Настоящий OpenAI и Google Calendar не проверялись и не объявляются подключёнными. Ограничения запросов и output tokens заданы на сервере, но реальные расходы и лимиты аккаунта требуют настройки у провайдера.
- UI и accessibility проверены по исходникам. Проверка экранным диктором, клавиатурой в браузере, реальными мобильными экранами и пользовательскими данными остаётся для следующего разрешённого этапа.

После исправлений блокирующих замечаний в рассмотренной границе API/ИИ не осталось. Этот результат относится к выполненным проверкам и не означает, что публичное окружение уже готово или что найдены все возможные уязвимости.
